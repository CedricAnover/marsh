# v0.4.1 — Remote Execution Readiness

**Status:** Release candidate

v0.4.1 proves that Marsh's semantic execution model can cross a machine/process boundary without introducing a second workflow engine or committing the project to a production transport.

## Implemented

- transport-neutral `MachineConnection` protocol for connection/session concerns;
- `ExecutionSubstrate` protocol for machine-side execution capability;
- optional `Agent` protocol for machine-side execution endpoints;
- identity-preserving `ExecutionRequest` and `ExecutionResponse` messages;
- explicit remote reconciliation that preserves ambiguous outcomes when transport evidence is insufficient;
- a small standard-library TCP reference adapter for communication conformance;
- local and Docker machine metadata/capability surfaces aligned with the new boundary;
- cross-process identity and remote-boundary tests;
- Docker user-defined-network communication conformance test;
- README, architecture, semantic-contract, and documentation-index updates;
- package version `0.4.1`.

## Scope

The release is deliberately transport-neutral. It does **not** add a production remote control plane, distributed scheduler, durable remote state service, gRPC/Protocol Buffers dependency, or mandatory remote infrastructure.

The reference TCP adapter exists to prove communication semantics, not to establish TCP/JSON as the long-term production transport.

## Conformance ladder

1. in-process contract tests;
2. separate local processes;
3. localhost TCP communication;
4. isolated Docker-network communication;
5. explicit transport-failure and identity-mismatch handling;
6. cross-platform portable socket/process tests.

Cross-OS verification remains dependent on the repository's Windows portability CI gate. Docker-network verification requires a Docker-capable CI executor.

## Semantic invariants

- Workflow semantics remain provider-independent.
- Execution identity is independent of PID/provider-local handles.
- Attempt identity remains distinct from execution identity.
- Transport errors do not automatically become process failures.
- Missing authoritative evidence remains ambiguous.
- Lifecycle/result semantics remain those of the existing kernel.
- Optional provider dependencies remain outside core runtime dependencies.
- The remote boundary does not introduce another scheduler or workflow engine.

## Verification

Required release evidence: targeted remote-boundary tests; full pytest suite; lint; package build; Docker integration/conformance; SSH integration regression coverage; Linux and Windows portability; dependency-boundary checks; security/redaction review; exact artifact/version verification; and main/develop synchronization.

## Technical lessons

### Transport is not the semantic boundary
A socket, SSH session, RPC framework, or container network is only a mechanism. The durable contract must be defined in terms of identity, lifecycle, results, capabilities, and reconciliation first.

### Ambiguity is a first-class state
A connection failure after dispatch cannot prove whether work failed. The runtime must preserve uncertainty until an authoritative observation resolves it.

### Identity must cross the boundary explicitly
Execution and attempt identifiers must be carried in boundary messages. Provider handles, PIDs, container IDs, and connection objects are local observations, not semantic identity.

### Conformance needs real boundaries
In-process mocks are insufficient for communication work. Separate processes, real sockets, and isolated container networks expose serialization, framing, lifecycle, and cleanup problems that unit tests cannot.

### Reference mechanisms should remain replaceable
The stdlib TCP adapter provides inexpensive evidence while keeping production transport selection reversible.

### Documentation must describe the implemented boundary
Public documentation distinguishes implemented v0.4.1 contracts from future distributed execution so a conformance mechanism is not mistaken for a production architecture.

## Exit criterion

v0.4.1 is complete when the remote boundary conformance suite and all repository release gates are green, documentation matches the implementation, release artifacts are verified, project tracking is synchronized, and temporary development infrastructure has been deleted.
