# v0.3.7 — Policies & Runtime Control

## Highlights

- Hardened the canonical execution-policy model.
- Added backend-independent retry, timeout, cleanup, cancellation, restart, scheduling, and resource policy data.
- Added deterministic policy evaluation and terminal-outcome precedence.
- Added attempt numbers and attempt identities to runtime results.
- Normalized cleanup-before-retry behavior and conservative retry safety for non-idempotent tasks.
- Preserved timeout and cancellation distinctions and exposed lifecycle event types.
- Added Workflow policy data to the marsh.workflow/v1 boundary.
- Added deterministic policy, retry, cleanup, IR round-trip, and safety tests.

## Semantics

The runtime sequence is: execute one attempt -> accept the observed terminal outcome -> run cleanup at most once -> evaluate retry eligibility -> either start a new attempt with a new attempt identity or return the final result.

Cleanup failure does not rewrite the primary result and blocks automatic retry by default. Non-idempotent operations are not retried unless explicitly allowed. Cancellation requires backend confirmation; timeout remains a distinct outcome.

## Compatibility

The existing scheduler, provider, machine, and process contracts remain the execution mechanisms. v0.3.7 does not introduce a second runtime or scheduler.

Policy data is serializable through the existing marsh.workflow/v1 document boundary. Runtime-only callbacks are intentionally excluded from portable policy data.
